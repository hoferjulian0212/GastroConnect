GastroConnect – Local, Sustainability, Zero-Waste & Logistics Intelligence Integration

0. WICHTIG: ERST VERSTEHEN, DANN ÄNDERN

Du arbeitest als Senior Full-Stack Developer / Product Architect an der bestehenden GastroConnect-Anwendung.

DO NOT immediately start coding.

Bevor du irgendetwas veränderst, musst du die bestehende Anwendung vollständig analysieren und verstehen.

GastroConnect ist bereits eine funktionierende Anwendung mit bestehenden User Roles, Workflows, Datenmodellen, Bestellungen, Lieferanten, Restaurants, Produkten, Lagerfunktionen, Lieferlogik, Fahrer-App usw.

Die Aufgabe ist NICHT, eine neue App zu bauen.

Die Aufgabe ist:

Die bestehende GastroConnect-App gezielt um eine Local / Sustainability / Zero-Waste / Logistics Intelligence Layer zu erweitern, ohne bestehende Funktionen, Datenmodelle, Workflows oder UI-Prinzipien unnötig zu verändern oder zu duplizieren.

Die bestehende App soll danach weiterhin wie dieselbe App funktionieren – nur intelligenter, informativer und strategisch stärker.

2. KEINE DUPLIKATION VON DATEN ODER LOGIK

Das ist eine der wichtigsten Anforderungen.

Bevor du neue Variablen, Felder, Tabellen, Functions oder Services erstellst:

Prüfe immer zuerst, ob die benötigte Information bereits existiert.

Beispiele:

Wenn bereits ein Product origin, supplier, category, deliveryZone, price, stock, distance etc. besitzt:

KEIN zweites paralleles Datenmodell erstellen.

Wenn bereits Delivery Distance oder ETA berechnet wird:

Diese bestehende Logik wiederverwenden oder erweitern.

Wenn bereits Risk Stock existiert:

Daraus das spätere Rescue-/Low-Waste-System aufbauen, nicht ein neues unabhängiges Inventory-System entwickeln.

Wenn bereits Supplier Location / Restaurant Location existiert:

Diese Daten für Local Score und Logistics verwenden.

Wenn bereits Order Dates / Delivery Dates existieren:

Diese Daten für Route Optimization und Delivery Efficiency verwenden.

* Entfernung

* Verpackung

22. DELIVERY ROUTE INTELLIGENCE

Das bestehende Routing-System ist bereits vorhanden.

Es soll nicht ersetzt, sondern erweitert werden.

Aktuell:

Route optimization / ETA / Stops.

Neu:

Route Efficiency

* total distance
* number of stops
* delivery density
* route fill rate
* consolidated deliveries
* estimated CO₂
* potentially avoided distance

Beispiel:

Route 24

8 stops
76 km
89 % route efficiency

Estimated:

−18 % distance vs. separate deliveries

Die genaue Methodik muss sauber definiert und dokumentiert werden.

⸻

23. CO₂ CALCULATION

Nicht einfach irgendeinen CO₂-Wert anzeigen.

Erstelle eine klar getrennte Calculation Layer:

Inputs

* vehicle type
* estimated distance
* route distance
* number of stops
* load/utilization, falls verfügbar
* existing delivery data

Output

Estimated delivery emissions

und optional:

Estimated emissions avoided through consolidation

Immer klar als estimated kennzeichnen, solange keine echten Fahrzeug-/Fuel-/Telematics-Daten vorhanden sind.

* gewünschtes Lieferdatum
* gewünschte Lieferzeit
* Restaurant availability window

Die bestehende Order Logic muss vollständig berücksichtigt werden.

Wenn ein Restaurant sagt:

darf daraus NICHT automatisch entstehen:

Mon–Fri
07:00–12:00
14:00–18:00

Wenn eine Bestellung „ASAP“ gewählt wird, muss das Routing diese Verfügbarkeit berücksichtigen.

Wenn ein fixes Lieferdatum gesetzt wurde:

Dieses Datum darf nicht durch Route Optimization verändert werden.

25. ROUTE CONSOLIDATION

* gleiche/nahe Zone
* kompatibles Lieferfenster

kann GastroConnect sie bündeln.

Beispiel:

Restaurant A
Restaurant B
Restaurant C

→ gleiche Tour.

Das bestehende Routing muss dabei die bestehenden Business Rules behalten.

36. DO NOT OVERENGINEER

Ein zentraler Grundsatz:

GastroConnect soll nicht zu einer Sustainability Dashboard App werden.

Der Marketplace bleibt das Produkt.

Sustainability ist eine intelligente Ebene, die den Marketplace besser macht.

Der Nutzer soll nicht denken:

„Ich muss jetzt Nachhaltigkeit verwalten.“

Sondern:

„Ich bestelle wie immer – GastroConnect zeigt mir automatisch die bessere Option.“

⸻

37. DO NOT LOSE THE PLOT

Die übergeordnete Vision lautet:

GastroConnect macht regionale Gastronomie digital effizienter, nachhaltiger und messbarer, ohne den Einkaufsprozess komplizierter zu machen.

Jede neue Funktion muss gegen diese Frage geprüft werden:

Does this make GastroConnect:

* more local?
* less wasteful?
* more efficient?
* more data-driven?
* easier to use?
* more valuable for restaurants?
* more valuable for suppliers?
* more useful for logistics?

Do not implement it just because it sounds innovative.

„Dieses Produkt ist nachhaltig.“

4. Identify conflicts / duplication risks.
5. Propose the exact integration points.
6. Only then implement the features according to P0 → P1 → P2 priority.

If you discover that an existing feature already solves part of a requirement, extend it instead of creating a parallel feature.

If a requested feature cannot currently be calculated reliably from existing data, do not fake it. Identify the missing data and create the smallest sensible extension required to make it measurable later.

The goal is not maximum feature count.

The goal is:

A cleaner, smarter, more local and more sustainable GastroConnect without losing the simplicity and speed of the existing product.
