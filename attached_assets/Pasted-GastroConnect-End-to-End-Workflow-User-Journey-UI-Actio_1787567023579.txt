GastroConnect – End-to-End Workflow, User Journey, UI Action & State-Flow Audit

OBJECTIVE

Perform a complete end-to-end workflow audit of the existing GastroConnect application.

This audit is specifically about:

* user journeys
* workflow clarity
* state-dependent actions
* button visibility
* button availability
* redundant actions
* conflicting actions
* dead buttons
* dead code
* impossible actions
* skipped workflow steps
* incorrect transitions
* inconsistent terminology
* inconsistent behavior between pages
* unclear responsibility between Restaurant and Supplier users
* unclear responsibility between different Supplier users
* unclear responsibility between Admin and normal users
* complaints and issue handling
* order processing
* delivery processing
* product management
* pricing
* supplier/restaurant interactions
* documents
* invitations
* all other existing GastroConnect features

The goal is NOT to redesign GastroConnect.

The existing:

* business logic
* order statuses
* complaint statuses
* roles
* workflows
* terminology
* database model
* core functionality

must remain the source of truth.

First understand what the application currently does.

Then identify inconsistencies and bugs.

Then correct the implementation so that the EXISTING intended workflow is clear, deterministic and difficult to misuse.

⸻

1. CRITICAL RULE: DO NOT INVENT A NEW WORKFLOW

Before changing anything:

Inspect the existing codebase and determine:

* all entities
* all statuses
* all roles
* all transitions
* all buttons
* all actions
* all API endpoints
* all state-changing operations
* all pages
* all modals
* all forms
* all workflows

Do NOT invent new statuses.

Do NOT rename statuses.

Do NOT invent new business processes.

Do NOT remove functionality merely because it is not obvious.

First determine what the existing application intends to do.

If two parts of the application contradict each other, identify the contradiction and resolve it in favor of the established/current business logic.

If something is genuinely ambiguous, document it instead of inventing a business rule.

⸻

2. CORE PRINCIPLE

A user should always know:

1. What is the current state?
2. What am I responsible for?
3. What is the next action?
4. What happens if I click it?
5. What does the other party need to do afterward?
6. What actions are currently unavailable?
7. Why are they unavailable?
8. When do they become available?

The interface should guide the user through the workflow.

Do NOT present users with 10 buttons when only 1 meaningful action is appropriate.

⸻

3. STATE = AVAILABLE ACTIONS

Every entity with a workflow/status must have a deterministic action matrix.

For every status:

* determine what actions are allowed
* determine who can perform them
* determine what actions are forbidden
* determine what actions should be hidden
* determine what actions should be disabled
* determine what happens after the action
* determine what the other user sees afterward

Do not rely only on frontend visibility.

Backend must enforce the same rules.

⸻

4. HIDDEN VS DISABLED ACTIONS

Use a consistent rule.

If an action is completely irrelevant to the current state:

Hide it.

Example:

An order has not yet been accepted.

Do not show unrelated delivery-completion controls.

If an action is conceptually relevant but currently unavailable because of a missing prerequisite:

Disable it and explain why, if useful.

Example:

Assign Driver

disabled because:

Order must first be accepted.

Do not show confusing combinations of active buttons that allow users to skip the intended workflow.

Treat every GastroConnect workflow as a conversation between users and the system.

Example:

RESTAURANT
"Here is my order."
        ↓
SYSTEM
"Order received."
        ↓
SUPPLIER
"This order requires my action."
        ↓
SYSTEM
"Supplier has accepted the order."
        ↓
RESTAURANT
"Supplier accepted it."
        ↓
SUPPLIER
"Now I need to perform the next relevant step."
        ↓
SYSTEM
"That step is complete."
        ↓
RESTAURANT
"Delivery is progressing."
        ↓
DELIVERY
"Order delivered."
        ↓
SYSTEM

        ↓
COMPLAINT (if necessary)

        ↓

        ↓

At EVERY transition:

WHO acts → WHAT can they do → WHAT happens → WHAT status results → WHAT does the other user see → WHAT can they do next → WHAT actions disappear

That logic must be reflected consistently in:

* frontend
* backend
* database/state machine
* permissions
* buttons
* menus
* modals
* notifications
* navigation
* API endpoints

The final result should feel like a guided professional workflow rather than a collection of independent features.

Do not change the underlying GastroConnect business model.

Make the existing system deterministic, coherent, clean and impossible to accidentally skip or break through normal UI usage.
