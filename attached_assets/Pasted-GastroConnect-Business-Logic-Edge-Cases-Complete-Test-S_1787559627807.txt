GastroConnect – Business Logic, Edge Cases & Complete Test Specification

OBJECTIVE

I want you to audit the entire existing GastroConnect application and implement/test robust business logic for all realistic scenarios.

Do NOT assume that the current implementation is correct.

First inspect the complete existing application:

* frontend
* backend/API
* database schema
* authentication
* authorization
* user roles
* order lifecycle
* products
* supplier logic
* restaurant logic
* price lists
* delivery zones
* postal-code logic
* ETA logic
* documents/uploads
* invitations
* admin functions
* notifications
* maps
* search/filtering
* error handling
* state transitions
* data validation
* concurrency
* persistence

Do not rewrite working functionality unnecessarily.

The goal is to make GastroConnect behave like a reliable production SaaS application rather than a prototype.

For every rule below:

1. Check whether the functionality already exists.
2. If it exists, verify that it behaves correctly.
3. If it does not exist, implement it using the existing architecture.
4. Do not duplicate existing functionality.
5. Do not break existing functionality.
6. Add tests where appropriate.
7. Enforce security rules on the SERVER/BACKEND, not only in the frontend.
8. Never trust IDs, prices, roles, permissions, quantities or other business-critical values supplied by the client.
9. Never rely only on UI restrictions for security.

⸻

1. CORE PRINCIPLE

Every important user action must have a defined state transition.

For every action determine:

* Who can perform it?
* Under what conditions?
* What data is changed?
* What data must not change?
* What happens if the action fails?
* What happens if the user performs it twice?
* What happens if two users perform it simultaneously?
* What happens if the user reloads the page?
* What happens if the network disconnects?
* What happens if the referenced object was deleted/changed?
* What happens if the request is manipulated manually?
* What happens if the user is unauthorized?

No important business operation should depend solely on frontend state.

⸻

2. MULTI-TENANT SECURITY

GastroConnect contains multiple restaurants and suppliers.

Restaurant A must NEVER be able to access Restaurant B’s private data.

Supplier A must NEVER be able to access Supplier B’s private data unless explicitly intended.

Implement and test tenant isolation for:

* orders
* order items
* customer data
* restaurant data
* supplier data
* private prices
* price lists
* delivery settings
* documents
* invoices
* addresses
* users
* invitations
* internal notes
* analytics
* statistics
* private configuration

Test direct API manipulation.

Example:

Restaurant A must not be able to access Restaurant B simply by changing:

restaurantId

in an API request.

The backend must verify ownership/authorization independently of the frontend.

⸻

3. USER ROLES

Known roles:

* Restaurant Buyer
* Supplier Seller
* Admin

Define explicit permissions for every role.

Restaurant Buyer

Should generally be able to:

* manage its own organization information
* manage authorized users
* browse suppliers
* browse products available to the restaurant
* see applicable prices
* create orders
* manage its own carts
* see its own orders
* see order status
* upload permitted documents
* see permitted supplier information
* interact with suppliers according to the defined workflow

Must NOT:

* modify supplier products
* modify supplier prices
* access another restaurant’s orders
* access another restaurant’s private price list
* change its own role to Admin
* change its own organization to another restaurant
* access supplier private data
* access system-wide administration

Supplier Seller

Should generally be able to:

* manage its own company
* manage its products
* manage applicable prices
* manage delivery zones
* receive relevant orders
* update permitted order statuses
* manage permitted documents
* see its own customers/orders

Must NOT:

* modify another supplier’s products
* see another supplier’s private customer information
* modify restaurant data without authorization
* access Admin functions
* manipulate another supplier’s orders

Admin

Admin permissions should be explicitly defined.

Do not automatically assume that “Admin” means unrestricted access to every database table.

Every administrative action should be audited where appropriate.

4. AUTHENTICATION

Test:

* valid login
* invalid password
* invalid email
* nonexistent user
* empty credentials
* malformed email
* expired session
* logout
* logout and browser back
* refresh after login
* refresh after logout
* session persistence
* session expiration
* unauthorized API request
* deleted user
* disabled user
* user whose organization was deleted/disabled
* user whose role changed while logged in

If authentication expires while a user is editing something:

* do not silently submit unauthorized changes
* handle the expired session cleanly
* preserve user-entered information where reasonably possible

Never expose sensitive authentication information in frontend errors.

⸻

5. USER INVITATIONS

Implement robust invitation behavior.

Cases:

New invitation

Restaurant/Supplier/Admin invites a user.

Expected:

* invitation is generated
* invitation belongs to correct organization
* invitation has expiration
* invitation cannot be reused after acceptance
* invitation cannot be used by an unauthorized organization

Duplicate invitation

Same email invited twice.

Do not create uncontrolled duplicate active invitations.

Either:

* reuse/update existing invitation
* or clearly reject duplicate

depending on existing product design.

Expired invitation

Expired invitation must not create access.

Already registered email

Handle correctly.

Do not accidentally transfer the user between organizations.

Invitation accepted twice

Second attempt must fail safely.

Invitation token manipulation

Invalid token must fail.

User changes organization ID manually

Must be rejected server-side.

Invitation after organization is disabled

Must not create new access.

⸻

6. USER / ORGANIZATION DELETION

Never blindly delete data that is referenced by historical transactions.

Before deleting:

* determine dependencies
* preserve historical orders where required
* preserve audit information where required
* prevent broken foreign references

Prefer:

* deactivate/archive
* soft delete

for business-critical entities where historical records must remain.

Test:

* delete user with orders
* delete supplier with orders
* delete restaurant with orders
* delete product referenced by historical orders
* delete price list referenced by historical orders

Historical orders must remain understandable.

⸻

7. PRODUCT MANAGEMENT

Supplier creates product.

Validate:

* name
* SKU/product code if applicable
* unit
* category
* price
* availability
* supplier ownership

Reject:

* missing required fields
* invalid price
* negative price
* NaN
* infinite numbers
* invalid quantity
* malformed IDs
* unauthorized supplier ID

⸻

8. PRODUCT DUPLICATES

Test:

* same product name
* same SKU
* same supplier + same SKU
* same product created twice by double-click
* same product created simultaneously by two browser sessions

Define uniqueness rules.

Do not rely only on frontend validation.

Database-level constraints should be used where appropriate.

⸻

9. PRODUCT DEACTIVATION

Supplier deactivates product.

Questions to enforce:

* Can restaurants still see it?
* Can it be added to a new cart?
* Can an existing cart contain it?
* Can an existing order containing it remain valid?

Recommended business behavior:

A product becoming unavailable must NOT corrupt historical orders.

Historical order items retain their historical product information.

⸻

10. PRODUCT PRICE CHANGES

This is extremely important.

Example:

Restaurant orders Product A for €10.

Supplier changes Product A to €12.

The existing order must remain €10.

Never calculate historical order totals dynamically from the current product price.

Store the relevant historical values in the order/order-item record.

Test:

1. Add product at €10.
2. Change product to €12.
3. Submit order.
4. Verify correct intended price according to checkout rules.
5. Verify historical order remains correct.
6. Reload.
7. Reopen order.
8. Verify price did not unexpectedly change.

⸻

11. PRICE LISTS

GastroConnect supports restaurant-specific pricing.

Test:

Supplier standard price = €10.

Restaurant A price = €8.

Restaurant B price = €9.

Restaurant C = standard price.

Verify:

* A sees €8
* B sees €9
* C sees €10

Restaurant A must never see Restaurant B’s private price.

Changing Restaurant A’s price must not change Restaurant B’s price.

Deleting a price list must have defined behavior.

Changing the supplier’s standard price must not unexpectedly overwrite restaurant-specific prices.

⸻

12. PRICE PRIORITY

Define one deterministic price resolution hierarchy.

For example:

1. Restaurant-specific price
2. Supplier standard price
3. Product unavailable / no price

Do not allow multiple prices to be selected randomly.

If conflicting price records exist:

* detect conflict
* choose deterministic behavior
* log/report the problem
* never silently charge an arbitrary price

⸻

13. PRICE VALIDATION

Reject:

* negative prices
* invalid decimals
* NaN
* Infinity
* malformed numeric strings
* absurd values beyond configured business limits

Use decimal-safe monetary handling.

Avoid floating-point arithmetic for financial totals where possible.

Example:

€10.10 + €10.20 must reliably equal €20.30.

⸻

14. CART

Cart belongs to the correct restaurant/user context.

Test:

* add product
* remove product
* change quantity
* empty cart
* refresh page
* logout/login
* supplier changes product
* product becomes unavailable
* price changes
* delivery zone changes
* product deleted/deactivated

Cart must never contain unauthorized products.

⸻

15. CART QUANTITIES

Test:

* quantity 1
* quantity 0
* negative quantity
* decimal quantity if not allowed
* extremely large quantity
* non-numeric quantity
* rapid quantity changes
* double-click
* simultaneous updates

Never trust frontend quantity.

Backend validates it.

If quantity becomes 0:

* either remove item
* or reject

but never create an invalid order item.

⸻

16. ORDER CREATION

Order creation must be transactional.

A successful order should not end up half-created.

Possible failure:

Restaurant submits order.

Database writes order.

Then order items fail.

This must not leave a broken order unless the system intentionally supports draft/partial states.

Use transactions where appropriate.

⸻

17. DOUBLE ORDER SUBMISSION

Critical.

User clicks:

Place Order

twice.

Or:

* double-click
* browser retries
* mobile reconnects
* network timeout causes user to retry

Result must NOT be two identical orders.

Use idempotency/request protection where appropriate.

Test this explicitly.

⸻

18. ORDER TOTAL

Order total must be deterministic.

Example:

Product A × 2 = €20

Product B × 3 = €15

Total = €35

Test:

* quantity changes
* price changes
* product removal
* rounding
* discounts if applicable
* delivery fees if applicable
* commissions if applicable

The final persisted order total must not depend on current product data after creation.

⸻

19. ORDER SNAPSHOT

At order creation, preserve relevant historical information:

* product name
* SKU if applicable
* unit
* price
* quantity
* subtotal
* applicable customer/supplier context
* delivery information
* relevant addresses

Historical orders must remain readable even if the product later changes.

⸻

20. ORDER STATUS MACHINE

Create an explicit allowed status transition system.

Do NOT allow arbitrary status changes.

Example conceptual flow:

Draft

→ Submitted

→ Accepted

→ Preparing

→ Dispatched

→ Delivered

Possible cancellation/rejection states must be explicitly defined.

For every status:

* define who can set it
* define allowed previous states
* define allowed next states
* define whether the transition is reversible

Example:

Delivered → Submitted

must not be possible.

⸻

21. INVALID ORDER TRANSITIONS

Test:

* Delivered → Accepted
* Delivered → Cancelled
* Rejected → Accepted
* Cancelled → Accepted
* Dispatched → Draft
* Accepted → Draft

Unless explicitly allowed, reject these transitions server-side.

Frontend hiding a button is insufficient.

⸻

22. SIMULTANEOUS ORDER STATUS CHANGES

Restaurant and supplier perform actions at nearly the same time.

Example:

Supplier accepts order.

Restaurant cancels order at the same time.

The backend must resolve the conflict deterministically.

Never allow:

* corrupted state
* two contradictory final states
* duplicated status history

Use transactional/concurrency-safe logic.

⸻

23. ORDER CANCELLATION

Define cancellation rules.

Test cancellation:

* before submission
* after submission
* after acceptance
* after preparation
* after dispatch
* after delivery

If cancellation is allowed only until a specific status, enforce that server-side.

Do not merely hide the cancel button.

⸻

24. ORDER REJECTION

Supplier rejects order.

Require reason if product design requires it.

Restaurant sees:

* rejected status
* rejection reason
* timestamp

Supplier must not be able to modify another supplier’s rejection.

⸻

25. ORDER HISTORY

Historical orders must survive:

* product deletion
* product price change
* supplier product edit
* restaurant user deletion
* supplier user deletion
* organization metadata changes

The order should remain an immutable historical record except for explicitly allowed fields.

⸻

26. ORDER ACCESS

Restaurant sees:

* its own orders

Supplier sees:

* orders belonging to that supplier

Admin sees according to admin permissions.

Test direct URL manipulation:

/orders/OTHER_ORDER_ID

Must return unauthorized/not found.

Do not leak whether a private order exists if security policy requires non-disclosure.

27. DELIVERY ZONES / POSTAL CODES

* valid postal code

* empty postal code
* lowercase/uppercase irrelevant characters
* spaces
* malformed input
* leading/trailing whitespace
* unknown postal code
* supplier serves exact postal code
* supplier does not serve postal code

Normalize postal codes consistently.

Do not let different formatting accidentally bypass delivery rules.

⸻

The existing order must NOT suddenly become invalid.

Historical order delivery conditions should remain stable once the order is accepted/created according to business rules.

New orders must use the current delivery configuration.

CRITICAL.

68. DATA RACE EXAMPLE

Restaurant has Product A in cart at €10.

* update cart

69. PRICE RACE EXAMPLE

Restaurant sees €10.

Restaurant checks out.

70. DELIVERY RACE EXAMPLE

Frontend state must not make an operation appear successful when database state is different.

79. CACHE INVALIDATION

If caching is used:

After:

* price change
* product deactivation
* delivery-zone change
* order status change

cached data must not remain incorrectly stale beyond defined behavior.

⸻

80. TIME / DATE

Define timezone behavior.

GastroConnect is intended for South Tyrol/Italy initially.

Use a consistent timezone strategy.

Test:

* order timestamps
* status timestamps
* invitation expiration
* delivery dates
* daylight saving time
* date displayed differently between frontend/backend

Never rely blindly on browser local time for server-side business logic.

⸻

81. ORDER TIMESTAMPS

Preserve:

* createdAt
* updatedAt
* status transition timestamps where relevant

Do not allow ordinary users to manipulate these timestamps.

⸻

82. HISTORICAL IMMUTABILITY

Once an order becomes historical, do not allow current master data to rewrite history.

Changing:

* product name
* price
* SKU
* supplier name
* restaurant name

must not unexpectedly alter historical order facts that need to remain immutable.

⸻

83. ORDER DOCUMENTS

If invoices/delivery documents are attached to orders:

Ensure:

* correct organization access
* correct order association
* correct permissions
* deletion rules
* historical availability

⸻

84. SEARCH + SECURITY

Search results must be permission-filtered BEFORE returning results.

Do not:

1. retrieve all suppliers
2. hide unauthorized suppliers in frontend

Instead:

backend/database query should only return authorized records.

⸻

85. ERROR + RETRY UX

For every important failed operation:

Show:

* what happened
* whether data was saved
* whether retry is safe

Example:

If order submission times out:

Do NOT simply say:

Order failed.

when the server may have already created it.

Instead verify the transaction state or use idempotency.

⸻

86. BROWSER MULTI-TAB

Test same account in two tabs.

Examples:

Tab A edits product.

Tab B deletes/deactivates product.

Tab A saves.

System must handle stale data safely.

Also test:

* two tabs submitting same order
* two tabs changing quantity
* two tabs changing order status

⸻

87. MOBILE / RESPONSIVE

Even though this is a webapp:

Test business operations on smaller screens.

Critical buttons must not be accidentally double-clicked due to UI layout.

Forms must remain usable.

Every form should validate:

* required fields
* data type
* length
* format
* range
* relationships

Frontend validation improves UX.

Backend validation guarantees correctness.

Both should exist.

93. IMPORTANT TEST PHILOSOPHY

Do NOT only test:

“Does the feature work when used correctly?”

Also test:

“What happens when the user does something stupid?”

“What happens when the user clicks twice?”

“What happens when the network dies?”

“What happens when two users do it at once?”

“What happens when the user changes the ID manually?”

“What happens when the database contains something unexpected?”

“What happens when the related object no longer exists?”

“What happens when the user is no longer authorized?”

“What happens if an external service fails?”

“What happens if the browser reloads at exactly the wrong moment?”

These are the scenarios that separate a prototype from production software.
